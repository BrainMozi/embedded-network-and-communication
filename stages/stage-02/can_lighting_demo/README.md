# 基于 CAN 的分布式汽车灯光控制系统

本项目对应《车载网络与协议-第二讲》实战：在 Ubuntu 上用 Python、`python-can` 和 Linux SocketCAN 虚拟接口 `vcan0`，让控制端与独立灯光 ECU 进程通过真实 CAN 报文完成命令、执行、状态反馈和异常监控。所有灯具都以软件状态示意，不连接实体车灯。

## 最终展示

运行后自动打开本机实时面板，直接操作 8 种命令。页面同时展示车辆灯态、控制帧 `0x256`、ECU 任务事件、状态帧 `0x257`、命令序号、往返确认耗时、任务活跃情况和结构化日志。灯态由 ECU 实际发回的状态帧驱动，不是按钮端本地假状态。

```text
驾驶员按钮 → 控制端 CAN 0x256 → vcan0 → ECU 接收 / 队列 / 解析
           → 灯光控制任务 → 虚拟灯具状态 → ECU CAN 0x257 → 控制端序号匹配确认
```

操作记录保存在 `data/runs/<启动时间>/events.jsonl`，ECU 原始运行日志保存在同目录 `ecu.log`。另开终端可运行 `candump -ta vcan0`，观察原始总线帧。

## 五项任务与课件周期

| 任务 | 要求 | 程序中的实现 |
|---|---|---|
| CAN 命令接收 | 10 ms；事件驱动 | SocketCAN 阻塞接收，最多 10 ms 等待间隔；收到帧即唤醒 |
| 命令解析 | 事件驱动；消息队列 | 接收队列阻塞取帧、校验 DLC/命令/参数/保留位 |
| 灯光控制 | 5 ms；事件驱动 | 内部控制队列有消息即处理，5 ms 为队列等待/响应预算 |
| 状态反馈 | 20 ms；定时触发 | 每 20 ms 发送当前状态帧 `0x257` |
| 系统监控 | 100 ms；定时触发 | 每 100 ms 检查队列、通信计数、故障和期望/实际灯态 |

这里的 5/10 ms 是任务处理/等待预算，不是 Python/Linux 的硬实时保证。实际响应时间由运行时数据测量展示，不承诺实时操作系统级确定性。状态帧发送失败时 ECU 对该帧立即重试一次；控制端还会在命令未获应用反馈时重发原序号命令，ECU 负责去重与拒绝过期序号。

## CAN 应用帧

所有帧均为标准 11-bit CAN ID、DLC=8；CAN 控制器负责链路层 CRC 和帧 ACK。帧级 ACK 不代表灯光动作完成，应用确认依据是 `0x257` 的命令序号与实际灯态。

### 控制帧 `0x256`

| 字节 | 含义 | 说明 |
|---|---|---|
| 0 | 命令码 | 0 全关，1 全开，2 左转，3 右转，4 双闪切换，5 刹车灯切换，6 前大灯切换，7 尾灯切换 |
| 1 | 序号 | 8-bit，反馈帧回显，用于关联与重试去重 |
| 2 | 亮度参数 | 0–100；灯具仅为软件模拟 |
| 3–7 | 保留 | 必须为 0 |

左右转向互斥；双闪开启时左右同时进入警示模式；全关/全开针对六类灯光状态（左、右、双闪、刹车、前大灯、尾灯）。命令种类和灯光状态数量分开定义。控制端在 300 ms 未确认时最多重试两次，重试复用原序号；ECU 对重复帧去重、保留待确认回报队列，并拒绝过期序号，防止迟到重试覆盖较新的灯态。

### 状态帧 `0x257`

| 字节 | 含义 |
|---|---|
| 0 | 期望灯态位图（低 6 位） |
| 1 | 实际灯态位图（低 6 位） |
| 2 | 最近处理命令序号 |
| 3 | 最近命令码（无命令为 `0xFF`） |
| 4 | 结果：0 正常，1 命令校验拒绝，2 期望/实际灯态不一致（模拟故障） |
| 5 | 虚拟灯具故障位图（低 6 位） |
| 6 | 亮度参数 |
| 7 | ECU 接收帧计数低 8 位 |

位图顺序：bit0 左转向，bit1 右转向，bit2 双闪模式，bit3 刹车灯，bit4 前大灯，bit5 尾灯。

### 测试维护帧 `0x258`

仅用于本仿真的故障注入，byte0 为故障位图，其余字节为 0。它不是课件规定的驾驶员控制帧，也不替代 `0x256`/`0x257` 主链路。

## VS Code 开发与演示启动

现场按 VS Code 流程操作，不需要手工敲启动命令：

1. **File → Open Folder**，打开本目录 `can_lighting_demo/`。
2. 在 VS Code 选择项目解释器 `.venv/bin/python`。
3. 按 **Ctrl+Shift+B**，选择默认任务 **启动 CAN 灯光演示（Python）**。
4. VS Code 先运行 `scripts/setup_vcan.sh`，再用 `.venv/bin/python` 启动 `run_demo.py`、独立 ECU 和面板，并在 Ubuntu 桌面打开浏览器。
5. 停止时点击该 VS Code 任务终端的停止/垃圾桶按钮，或在终端菜单中选择 **Terminate Task**。不需要 Python 调试器，也不需要手动输入终端命令。

面板地址：`http://127.0.0.1:8765`。环境重建或依赖缺失时才需要运行 `scripts/install_deps.sh`；当前 VM 已完成安装。可选原始抓包脚本 `scripts/run_candump.sh` 仅作备用，常规演示无需额外终端。

`vcan0` 是 Linux 虚拟 CAN 接口；不需要 VMware 桥接、车辆 CAN 适配器或真实灯具。若 Ubuntu 重启导致接口消失，重新按 Ctrl+Shift+B 启动即可，预启动任务会自动重建它。

## 建议现场演示顺序

1. 展示 ECU 在线、`vcan0`、任务状态与持续的 `0x257` 状态帧。
2. 点击左转：观察 `0x256` 发送 → ECU 接收/解析 → 灯态更新 → `0x257` 同序号回报，核对延迟。
3. 依次演示右转互斥、双闪、刹车/前灯/尾灯，以及全开/全关。
4. 勾选“虚拟灯具开路”后再次开启相应灯，观察目标/实际灯态不同、状态结果 2 和监控告警；取消故障后恢复。
5. 发送非法命令，观察解析拒绝与状态帧结果 1；观察 `candump` 原始报文、事件时间线与 `ecu.log`。
